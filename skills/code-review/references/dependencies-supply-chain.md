# Dependencies and supply chain

Use when: manifests, lockfiles, vendored code, base images, CI actions, package manager configuration or newly imported packages change.

## The questions

- Is the new dependency needed, or does the standard library or an existing dependency already do it?
- Is it the real package, from the expected registry, at a version that exists and is maintained?
- What code now runs at install, build and run time, and with what permissions?
- Does the lockfile change match the manifest change, and nothing else?

## New dependency

- **Need.** A whole package for a few lines of code, or a second library for something the project already has.
- **Identity.** Look-alike names, wrong scope or namespace, an internal package name that also exists publicly, and names that an AI assistant may have invented. Open the registry page: publisher, repository link, age, release history.
- **Health.** Last release, open advisories, number of maintainers, deprecation notices.
- **License.** Compatible with the project's policy. No license means no permission.
- **Install-time code.** Post-install scripts, build scripts, binaries downloaded during install.
- **Placement.** Runtime or development dependency, declared in the right place and the right workspace.
- **Weight.** Transitive tree and bundle size, when the change ships to a client or a constrained runtime.

## Version changes

- Major bumps: read the changelog for breaking changes in the APIs this code uses, and look for the adaptation in the diff.
- Unexplained downgrades.
- Loose ranges (`*`, `latest`, an open lower bound), git or URL dependencies with no pinned commit, local path dependencies.
- Pre-release versions in production dependencies.
- A security bump: confirm the target version contains the fix.
- Runtime or engine constraints that no longer match the deployed runtime or the CI image.

## Lockfile

- It changes together with the manifest. A lockfile-only change is either an explicit refresh or a red flag.
- Hundreds of unrelated transitive bumps inside a feature change: ask for a separate change.
- Registry hosts in resolved URLs that differ from the project's registry.
- An integrity hash that changed for an unchanged version.
- A lockfile deleted, ignored, or a second one from another package manager.
- Do not read lockfiles line by line. Compare the top-level changes and the hosts, and use the package manager's own tree and "why" commands.

## Vendored, copied and generated code

- A vendored update matches a named upstream version. Local patches are documented.
- Copied snippets carry their license and attribution.
- Generated files are regenerated by the tool, not edited by hand.
- A committed binary cannot be reviewed: ask what it is and where it came from.

## Build and CI supply chain

- Actions and reusable workflows pinned to a commit. Base images pinned by digest. Installers fetched over the network and piped to a shell.
- Package manager configuration changes: registries, script execution settings, authentication tokens in config files.
- Signing or provenance steps removed from release jobs.

## Removal

- A dependency removed but still used through a dynamic import, a plugin, a script or another workspace.

## Verify by

- A registry lookup instead of memory. Your knowledge has a cutoff: never claim a package or version does not exist without checking.
- The audit tool the ecosystem provides, when configured or cheap to run. Prefer tools that report whether the vulnerable code is reachable.
- Searching the diff for what is actually imported from the new package.
- Never installing packages from an untrusted change outside a sandbox: install scripts execute.

Pinning rules for workflows and images are in `infra-iac-ci.md`.

## Do not flag

- Routine patch and minor bumps from an update bot with passing CI, unless a repository rule asks for review.
- Transitive advisories with no reachable path, beyond one line in the handoff.
- "This could be written without a dependency" for substantial functionality.

## Priority guidance

P0: a package that does not exist or is not the intended one, a reachable known-exploited vulnerability introduced by the change, install-time code from an untrusted source, a license the project's policy prohibits, a registry redirected to an unexpected host, an integrity hash changed for the same version, tokens committed in package manager configuration. P1: a major bump with no sign of adaptation, an unpinned git dependency, an unexplained downgrade, a heavy dependency for a trivial need, unrelated lockfile churn. P2: an unused dependency, a development dependency declared as runtime.
